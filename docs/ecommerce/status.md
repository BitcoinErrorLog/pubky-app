# Marketplace Status: What Is Real and What Is Not

Read this before evaluating the marketplace. It exists so nobody has to reverse-engineer which behavior is genuine and which is simulated.

This is a **pre-production prototype under review**. It is not proposed for production, and nothing here has handled real funds.

Last updated: 2026-08-21.

| Nexus catalog discovery                                        | The catalog is populated from the Nexus listing stream (`GET /v0/stream/listings`, implemented on the `feat/marketplace-indexing` branch of `pubky-nexus`). The index now carries the full card projection — including the auction term fields (`auction_starts_at`/`auction_ends_at`, reserve, buy-now, minimum increment, all null for fixed-price) — so the grid renders straight from validated index entries, and the canonical record is fetched from the seller's homeserver only when a listing is opened (or when the index has seen a newer revision than the cache). The homeserver stays canonical per ADR 0020. Sale format, single-condition, and the ending-soon ordering (`sorting=ends_at`) run server-side; text search, hierarchical category, price range, and the remaining sorts stay client-side. Auction cards render the seller's terms (starting bid, buy-now, end date) from the index, which cannot know bid state. In `transaction-service` mode each auction card additionally reads the durable service's public listing projection **lazily, once, when it first scrolls into view** (`useMarketplaceLiveBid`): the service exposes only per-listing reads (`GET /v1/listings/{aggregate_id}`, no batch endpoint), so the cost is one request per auction card actually seen — never N eager requests on grid render, and nothing for off-screen cards. It is a point-in-time read, not a subscription; the detail page remains the polling surface. Only when the service reports ≥1 bid does the card relabel to "Current bid" with a bid count; zero bids keeps the honest "Starting bid" label, and an unreachable service (or missing session) silently degrades back to terms-only — a bid is never invented. Sandbox mode keeps terms-only cards; its simulated bid state appears on the detail page, where it is labeled. Auction rows indexed before Nexus carried the term fields serve null terms until the operator runs the Nexus auction-terms backfill (see the deployment row below); their cards render without the end-date/buy-now badges instead of guessing.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |
| Pricing currencies                                             | The sell studio deliberately offers two pricing assets: US dollars (`{currency: "USD", exponent: 2}`, cents as minor units) and bitcoin entered as whole base units (`{currency: "BTC", exponent: 8}` — the exact shape the live regtest purchase paid). The record schema itself accepts any uppercase asset code; the studio authors only these two, and refuses to edit (`unsupported`) a listing priced in an asset it cannot author rather than silently rewriting it. Offers, counters, and bids are always made in the listing's own asset — the record schema and the service reject cross-asset amounts. Bitcoin-denominated money renders per BIP-177 everywhere (`₿15,000` — the ₿ symbol with grouped integer base units); subtotals and seller revenue are reported per asset, never summed across assets. See [`pricing.md`](pricing.md). | Transaction-service transport & auth                           | Real Pubky auth: the SDK auth flow yields an `AuthToken` after signer approval, its bytes buy an opaque bearer session, commands go over snake_case wire per ADR 0019. Connect attempts time out after two minutes with a visible retry instead of awaiting forever. Verified end to end against the running service by `npm run test:marketplace:service`. | Encrypted messaging (durable modes)                            | **Real end-to-end encryption at experiment grade.** In `transaction-service` and `locks-paykit` modes, listing conversations run over Paykit Encrypted Links (Noise `XX_25519_ChaChaPoly_SHA256`) through the vendored browser WASM binding of the official paykit-rs messaging surface (`vendor/paykit-wasm`, provenance and checksums in [`paykit-wasm-provenance.md`](paykit-wasm-provenance.md)). The user enables messaging with its OWN Pubky Ring approval (`/pub/paykit/:rw` grant — separate from the transaction-service session); the identity secret never enters the browser, and link crypto uses a receiver-scoped Noise key generated and kept on this device. No service operator — including this marketplace's — can read message bodies; they travel and rest as ciphertext under DH-derived homeserver paths. Requirements and limits, disclosed in the UI: BOTH parties must have enabled messaging (published receiver markers) before anything can be delivered; a Noise XX handshake needs both runtimes, so the initiator cannot send until the counterparty's side answers (the UI says "waiting" instead of pretending); one message is capped at 1,000 bytes including its envelope (live byte budget in the composer, no attachments); history and the local key material (receiver Noise secret + link snapshots, stored UNENCRYPTED pending the backup-key decision) live only in this browser's account-scoped IndexedDB — no other device can show the conversation; the messaging session now survives a reload in the SAME tab (secret-free session metadata mirrored to per-tab `sessionStorage`, the credential itself is the browser's HTTP-only homeserver cookie, revalidated against the homeserver on restore — see `service-auth.md`, "Where the messaging session lives in the browser"), while a new tab, a new browser session, or an expired/revoked session still takes a fresh Ring approval. Proven by: real-crypto unit tests against the vendored artifact, a CI smoke gate, the binding's own 16/16 three-engine browser e2e at the pinned commit (including reload session restore), and LIVE two-party proofs driving the full client service stack — one against a local Pubky testnet (`npm run test:marketplace:messaging`) and one against the REAL staging homeserver (`ufibwbmed6jeq9k4p583go95wofakh9fwpp4k734trq79pd9u1uy`) over the public pkarr relays (`npm run test:marketplace:messaging:staging`, passed 2026-08-21 with `getTestnet() === false`, i.e. the exact client construction and topology of the staging deployment: token-gated signup, marker publish/discovery via `https://pkarr.pubky.app`, XX handshake, bidirectional chat, snapshot-restore). In both proofs only the interactive Ring approval leg is swapped for the binding's dev signup/signin helpers. Honest gaps: the live Ring-approval leg itself is unexercised, and upstream paykit-rs is pre-1.0 with no independent security review. |

| Watchlist, alerts & saved searches                             | **The watchlist IS the favorites store** (one concept: heart/bell on cards and listing pages, `/marketplace/watchlist` page) with account-scoped Dexie persistence. | Attested public reviews (durable, Phase 1–2 of the trust plan) | When the deployed transaction service holds an attestor key (ADR 0024; the Railway deployment does), `review.create` issues a **durable purchase attestation** — a compact JWS (EdDSA/Ed25519) whose claims (`iss`/`sub`/`cpk`/`role`/`listing`/salted `order_ref`/day-granularity `completed_on`/optional `amount_band`/`iat`) are specified normatively in the `pubky-app-specs` fork (`0.6.2-marketplace.3`, vendored). The client then builds the `PubkyAppMarketplaceReview` record via the specs builder, embeds the JWS in `eligibilityAttestation`, and **publishes it to the reviewer's own homeserver** (staged-job outbox; a failed PUT stays visibly pending and retries when the orders surface loads). The client re-runs the offline verification recipe (signature against the self-certifying `iss` pubky + claim bindings) before labeling the user's own review "Verified purchase" — the label claims exactly that and nothing more. `review.update` republishes with `revision + 1`; the attestation is unchanged (it attests the purchase, not the text). Amount bands follow the ratified **D2 both-sides consent**: a seller sets a standing preference on the service (`attestation.set_band_consent`), the buyer sees the per-review opt-in only when the seller consented (read honestly from `GET /v1/sellers/{pubky}/band-consent`), and the band is a log-decade (`USD:4`), never an exact amount. What this does NOT include yet: Nexus review indexing/aggregation, reputation on cards, seller responses UI, and third-party display of verified badges (plan Phases 2+/4); attestor-homeserver publication of annotations and weekly stat attestations is service-side data awaiting the Phase 3 publisher. ## Not done, and why

### Real payments: working with a simulated wallet; the Bitkit app UX is the one unproven leg

Real payments moved from deferred to **working, with the wallet's protocol role simulated by real tooling**. The composed environment (Lock Server, Paykit Server, Bitcoin regtest, Fulcrum, pinned Pubky testnet) exists and the whole purchase path is verified live in `locks-paykit` mode — see the Real table above and [`RUNNING.md`](RUNNING.md) for how to run it and the `npm run test:marketplace:locks` suite that proves it. The Locks browser SDK is vendored and generates the canonical bundle ids; the Locks network routes stay on the verified HTTP contract for the measured reasons in the Real table. What is missing is deliberate, not overlooked:

Precisely what "simulated wallet" means:

- **`paykit-companion-auth`** performs the `watch-only-account-v1` companion claim (Bitkit's approval role) with the seller's Pubky secret and a real bitcoind BIP84 account tpub — the same claim format the real wallet would send, without the phone.
- **`paykit-reader-demo`** receives the private Paykit Payment Request (Bitkit's protocol role) and returns the invoice's unique BIP84 address, independently re-derivable from the watch-only tpub.
- **The regtest node** executes the on-chain payment (any wallet can produce the amount-matched output; attribution is purely on-chain).

Everything protocol-side that a real wallet would talk to — invoice creation, private message delivery, address derivation, settlement observation, Locks completion, credential issuance, guarded reads, and the marketplace's independent server-side confirmation — is exercised for real. **The only unproven leg is the real Bitkit app UX**: approving the companion claim on a device, receiving and rendering the Payment Request in the app, and paying from its own wallet. That requires a person with a phone and cannot honestly be automated. Build provenance for the vendored Locks SDK is in [`locks-sdk-provenance.md`](locks-sdk-provenance.md).

### The durable service now backs the shopping UI — with deliberate gaps

The client's `transaction-service` mode covers authenticated sessions from Pubky AuthTokens, snake_case wire, the ported command set, and the service's role-scoped read projections (listings, offers, orders with embedded payment/shipment/return/dispute/refund/review sub-objects, payments, receipts, notifications, reports). Orders, offers, bids, checkout, and post-purchase actions operate against it: reads supply the `expected_revision` each command needs, and revision conflicts refetch and prompt a retry. What deliberately remains:

- **In-app session UX exists; the broader grant-UX question stays open.** Every durable-mode surface that needs a session now renders a "Connect marketplace session" affordance instead of a dead end: the dialog (`MarketplaceSessionConnectDialog`) states in one sentence what approval authorizes, shows the `pubkyauth://` URL as a QR for a cross-device Pubky Ring scan plus an "Open in Pubky Ring" deeplink and copy affordance (the same precedent as sign-in), waits with a cancel, and on failure shows the transport's real error with a retry that starts a FRESH flow (AuthTokens are single-use). On approval the session's public facts (never the token) mirror into the commerce store and the dependent surfaces refetch; a 401/expired session mid-action resurfaces the same affordance. What remains open in [`service-auth.md`](service-auth.md) is the product decision of whether this stays a separate approval or folds into sign-in — until then it is deliberately a second, explicit signer approval.
- **Payments in plain `transaction-service` mode stay on the sandbox adapter** — no Bitcoin in that mode, and the client refuses to send `payment.sandbox_advance` to the durable service at all, so a durable order honestly stays awaiting payment; the UI says exactly that instead of offering a simulate button. Real payments require `locks-paykit` mode, which composes with (never replaces) this mode's durable transport: the client registers the buyer's Locks correlation via `payment.register_locks` and the service's worker is the only thing that ever confirms a payment.
- **Redactions are honored, not papered over.** Read projections never carry `delivery_address` (the buyer sees it once, in their own checkout result) or `locks_bundle_id`; the seller-side packing slip consequently prints no address and says why, instead of pretending the seller was served one (see [`shipping.md`](shipping.md)); `receipt_id` is null until payment confirmation issues the receipt. Dispute evidence bodies stay out of every general projection and command result (only a count is visible there); the single exposure path is the scoped case-file read `GET /v1/orders/{id}/evidence`, served to exactly the two dispute participants and configured moderators — and that is the only source the UI ever renders evidence from. Moderator case-file reads are audited by the service in the same transaction as the read, and the UI discloses that to the moderator before and inside the case file.
- **Not served by the service, not faked by the client:** notification preferences have no durable tables and order cancellation commands are unported. Conversations/messages deliberately never got durable service tables — messaging in durable modes is end-to-end encrypted client-side (see Real), and the service never sees bodies or keys. The service-only `review.update` command now has a client contract and UI (see Real), gated to the durable mode and the 24-hour window.

So: what you click through in `transaction-service` mode is durable and authoritative; messaging is end-to-end encrypted client-side (experiment grade, labeled); and what is not available — payments in plain durable mode, notification read state/preferences, cancellation — is visibly labeled as unavailable or sandbox-only.

## Configuration implementers must set

### Moderators

The moderator set is **configuration, not code** — there is no hardcoded moderator identity. Supply the moderator pubky list to the transaction service via its documented environment configuration; entries are validated as z-base-32 pubkys at startup. An empty list means no one can access moderation queues, which is the correct default for a deployment that has not chosen moderators.

Moderation roles are independent: there is no broad admin role, and non-moderators cannot read another user's reports.

### Commerce adapter mode

`PUBKY_RUNTIME_COMMERCE_ADAPTER_MODE` defaults to `unavailable` and must stay that way outside explicitly local or demo deployments. See [`RUNNING.md`](RUNNING.md).

## How to judge this work

Fair questions to ask:

- Do public records belong to the user and survive without our infrastructure? (Yes — they are on your homeserver, and now specified.)
- Are the transactional invariants actually enforced, or asserted? (Enforced by database constraints, with 100-way concurrency proofs.)
- Does the UI ever claim finality it does not have? (It should not; simulated states are labeled. Report any case that is not.)
- Could this take real money today? (Not in a normal deployment: the default mode fails closed, and `locks-paykit` refuses to activate unless every payment-rail URL is explicitly configured. The verified stack is regtest with a locally composed Lock Server and Paykit Server; nothing here has been pointed at mainnet, and doing so would first require the independent security review above.)
